### 2.2 适配理由

原生 PostgreSQL 与当前 `12`—`14` 设计的适配理由如下：

- `time_interval` 与 `time_interval_source` 的创建循环需要数据库延后约束触发器在事务提交前统一检查；PostgreSQL 原生支持约束触发器和可延后约束语义。
- Evidence 及后续投影任务需要条件唯一性时，PostgreSQL 原生支持部分索引；这与“只对有效状态建立唯一性”的逻辑相匹配。
- Canon Commit、来源绑定和恢复检查依赖短事务、行级锁、条件更新及明确的提交/回滚边界；PostgreSQL 的事务和行锁模型可以直接承接这些要求。
- 项目要求关系数据库作为权威数据源，图、向量和时间线为可重建投影；原生 PostgreSQL 不要求在第一批引入额外数据库或复杂中间件。

这些是适配理由，不等于已完成数据库产品批准、隔离级别批准或生产部署设计。

## 3. 实施工具与隔离测试方案

### 3.1 工具选择

仓库没有既有语言、依赖或迁移工具可以复用。由于本地已有 Node.js `22.23.2` 和 pnpm `11.18.0`，第一批推荐采用 Node.js 生态：

- 迁移工具：`node-pg-migrate`。
- PostgreSQL 客户端：`pg`。
- 测试执行：Node.js 内置 `node:test`，通过 `pg` 建立多个独立连接验证事务和并发。
- 迁移执行原则：从空库执行完整迁移序列；每次迁移有明确版本和可回滚/失败停留语义；测试不得依赖手工预置正式数据库对象。

以上依赖当前均未安装，本轮不安装。若项目后续正式选择其他应用语言，迁移工具必须重新评审；在没有明确批准前，不得同时维护两套迁移体系。

### 3.2 隔离测试数据库生命周期

后续实施时，测试只允许使用一次性隔离 PostgreSQL 实例，推荐流程为：

1. 使用固定的 PostgreSQL 18.x 测试镜像、随机本地端口和一次性容器名称启动测试实例；测试密码由测试进程临时生成，不写入仓库。
2. 使用容器内的就绪检查确认数据库已接受连接；不得使用随机 `sleep` 判断就绪。
3. 创建一个空测试数据库，并确认连接目标不是任何现有业务数据库。
4. 从空库执行第一批迁移，迁移阶段必须完成测试命名空间、夹具表、外键、唯一/CHECK 约束和延后约束触发器的创建。
5. 使用 Node.js 测试执行器运行约束、提交、回滚和并发测试；每项测试明确区分语句即时失败和真实 `COMMIT` 失败，并在独立连接中检查最终持久化状态。
6. 测试结束后停止并删除一次性容器及其临时数据卷，清理测试端口和临时凭据；不触碰用户目录中的其他数据库数据。

本轮没有启动数据库、没有创建测试数据库、没有执行迁移或测试，因此所有第一批测试状态均为“未执行”。

## 4. 第一批明确实施范围

### 4.1 范围选择

第一批明确选择：**Time Interval 来源绑定独立约束验证原型**。

该批次不是完整正式 Schema，也不是业务系统的首个可运行版本。原因是当前 `time_interval_source` 的完整来源集合横跨 Author Design、Candidate 和 Canon；直接实现完整正式 Schema 会同时引入大量尚未实施的业务表和迁移依赖。第一批先使用与 `12`—`14` 同名、同语义边界的最小测试夹具，验证真实数据库的延后约束、唯一性、事务提交和回滚行为；通过后再把约束迁入正式物理 Schema。

最小夹具必须明确标注为 `time_interval_constraint_fixture` 或等价测试命名空间，不得冒充正式业务表，不得作为正式 Schema 的替代事实源。

### 4.2 依赖对象、迁移顺序与测试写入顺序

从当前 `12`—`14` 推导，第一批需要验证的逻辑对象和依赖为：

| 层级 | 对象 | 第一批用途 |
|---|---|---|
| 区间 | `time_interval` | 保存区间本体、来源域、来源版本和时间值；不保存反向 `source_binding_id` |
| 来源绑定 | `time_interval_source` | 保存 `time_interval_id`、来源域、来源版本、来源类型及类型专属目标 FK；`time_interval_id` 必填且唯一 |
| Author Design 来源 | `temporal_constraint` | 验证 `temporal_constraint.interval_id` 与来源绑定一致 |
| Candidate 来源 | `candidate_version`、`candidate_event`、`candidate_fact_proposal`、`candidate_state_transition` | 验证 Candidate 容器、来源对象和区间引用/绑定归属；夹具只保留完整性检查所需字段 |
| Canon 来源 | `canon_commit`、`canonical_text_version`、`story_event`、`canon_fact`、`state_transition` | 验证 Commit、Novel、来源对象和区间引用/绑定归属；同事务创建的对象可参与提交前检查 |
| 约束执行 | 延后约束触发器及必要唯一/FK/CHECK 约束 | 覆盖区间、来源绑定和所有会引用区间的对象写入 |

**迁移阶段**只负责建立测试结构，不写入测试业务数据，顺序为：

1. 建立独立测试命名空间和最小夹具表。
2. 创建基础身份、项目/版本和来源对象表；必要时先建表，再补充跨表外键。
3. 创建 `time_interval`、`time_interval_source` 及类型专属目标列。
4. 创建主键、唯一、CHECK 和外键约束。
5. 创建覆盖 `time_interval`、`time_interval_source` 以及所有会引用区间或作为来源目标的对象写入的延后约束触发器。
6. 在所有测试开始前完成迁移；不得在单个测试事务中临时安装或关闭触发器、外键、唯一约束或 CHECK 约束。

**测试阶段**只负责事务内数据写入和验证，顺序为：

1. 开启事务。
2. 创建 `time_interval`。
3. 在同一事务内创建或复用需要引用该区间的来源对象。
4. 创建 `time_interval_source` 及其类型专属目标关系。
5. 执行即时约束检查或真实 `COMMIT`，由数据库决定语句失败或提交失败。
6. 使用独立连接检查最终状态。

区间无绑定只允许存在于未提交事务内部，不得通过提前提交半成品来制造测试前置数据。Canon 来源对象与区间可以在同一 Canon 原子事务内创建，不要求来源对象提前提交；相关失败时事务整体回滚。

### 4.3 不纳入第一批的内容

以下内容明确排入后续批次，不与本批混合实现：

- Evidence 完整来源身份和跨表唯一性；
- Projection Attempt 的成功接受、过期和 Checkpoint 推进；
- 完整 Canon Commit 原子事务及其全部 18 步；
- 图、向量、搜索和其他派生投影；
- 正式生产 Schema、分区、备份、灾备和部署拓扑。

## 5. 第一批验收计划

以下测试均为计划项，当前状态统一为“未执行”。每个负例只引入一种待验证错误，其他前置条件保持合法；如果先被其他约束拒绝，不计为目标延后约束测试通过。

失败阶段按以下规则记录：

- **即时失败**：主键、CHECK、FK 或非延后唯一约束在语句执行阶段失败。测试必须记录实际失败语句、SQLSTATE 和约束名，回滚后检查最终状态。
- **提交失败**：前置写入语句成功，延后约束触发器在真实 `COMMIT` 阶段失败。测试必须检查提交异常和整体回滚结果。
- 任何有限超时只表示测试执行失败或环境异常，不得算作约束通过；超时后必须清理连接和事务。
- 最终检查只验证本测试事务产生的变化。若场景要求先存在合法记录，则合法记录应继续存在，不得误判为需要删除。

| 验收项 | 输入与执行步骤 | 预期失败阶段／目标约束 | 预期结果 | 检查方式 | 状态 |
|---|---|---|---|---|---|
| 同事务创建区间、来源对象和绑定 | 单连接开启事务；按“区间 → 来源对象 → 来源绑定”写入合法 Candidate 或 Author Design 夹具后提交 | 成功路径；无失败 | `COMMIT` 成功；区间、来源对象和绑定均可从新连接读取 | 检查提交返回值，并在事务外查询完整关系 | 未执行 |
| Canon 同事务创建 | 单一 Canon 模拟事务中创建区间、Canon 来源对象和来源绑定 | 成功路径；不要求来源提前提交 | `COMMIT` 成功；相关关系完整 | 检查提交结果和事务外完整关系 | 未执行 |
| 仅创建区间 | 开启事务，只插入 `time_interval`，不插入 `time_interval_source` 后执行 `COMMIT` | 提交失败；延后 Time Interval 来源绑定约束 | `COMMIT` 失败；事务整体回滚 | 捕获提交异常，记录 SQLSTATE/约束名，并用第二连接确认区间不存在 | 未执行 |
| 顺序重复绑定 | 先在独立准备事务中提交完整合法的区间、来源对象和第一条绑定；测试事务尝试插入第二条绑定，第二条使用不同 `interval_source_id`，但复用同一 `time_interval_id`；若唯一约束在语句阶段失败，则记录后回滚测试事务，不再等待该事务提交 | 语句即时失败；`time_interval_source.time_interval_id` 非延后唯一约束 | 第二条绑定失败；原合法区间、来源对象和第一条绑定保留 | 记录失败语句、SQLSTATE 和唯一约束名；独立连接确认绑定数量仍为 1 | 未执行 |
| 并发创建完整记录：A 提交 | A 开启事务并写入完整区间、来源对象和绑定，保持未提交；B 开启事务并插入相同区间主键，确认 B 已通过锁状态或有限等待进入等待；随后 A 提交，B 继续并因区间主键唯一约束失败，最后清理测试事务 | B 语句失败；区间主键唯一约束；该场景不单独证明来源绑定唯一键并发语义 | A 提交成功；B 因区间主键冲突失败；最终只有 A 的完整来源链和 1 条绑定 | 使用显式 barrier/锁状态检查确认 B 等待；设置有限超时；记录 A/B 的 COMMIT 结果；独立连接检查完整记录和绑定数量 | 未执行 |
| 并发创建完整记录：A 回滚 | A 开启事务并写入完整区间、来源对象和绑定，保持未提交；B 插入相同区间主键并确认进入等待；随后 A 回滚，B 继续创建自己的来源对象和绑定并提交 | A 回滚后 B 可继续；目标为区间主键竞争和回滚释放锁 | A 不留下半成品；B 完成合法区间、来源链和唯一绑定并提交 | 使用显式 barrier/锁状态检查；设置有限超时；独立连接检查只有 B 的完整记录 | 未执行 |
| 即时约束负例：来源类型/目标字段不匹配 | 所有目标对象和容器均合法，只引入一个 `source_type` 与目标字段不匹配，或一个不存在目标的 FK/CHECK 错误 | 语句即时失败；目标 CHECK/FK 约束 | 错误语句失败；回滚后既有合法记录保持不变 | 记录失败语句、SQLSTATE、约束名和最终状态；不得把即时失败计为延后触发器测试 | 未执行 |
| 延后归属负例：版本/项目/容器不一致 | 所有即时 FK、CHECK 和唯一条件均合法，只引入一个跨表版本、项目或容器归属错误 | `INSERT` 前置写入成功；真实 `COMMIT` 失败；目标延后来源完整性触发器 | `COMMIT` 失败；相关事务整体回滚 | 记录提交异常、SQLSTATE、约束名，并用独立连接确认无半成品 | 未执行 |
| 来源对象区间引用不一致 | 所有对象均存在且其他字段合法，只让来源对象引用区间 A、来源绑定指向区间 B | 提交失败；来源对象引用与 `time_interval_source.time_interval_id` 一致性触发器 | `COMMIT` 失败；事务相关写入整体回滚 | 检查真实提交异常，并以独立连接确认没有半成品 | 未执行 |
| 最终校验失败后的回滚 | 先成功执行合法前置写入，再只破坏一个待验证的来源域/版本/项目或绑定关系后执行 `COMMIT` | 提交失败；延后来源完整性触发器 | `COMMIT` 失败；本事务所有相关写入均不存在 | 第二连接按本事务主键查询；不得要求删除测试前已存在的合法记录 | 未执行 |
| 并发同步与超时处理 | A/B 使用数据库屏障、锁状态查询或通知同步；不使用随机 `sleep`。B 等待确认有有限 deadline；deadline 到达即报告测试失败并清理 | 约束通过不能由超时推断 | 正常路径下得到明确 A 提交/B 失败或 A 回滚/B 成功结果 | 保存等待确认、释放锁、提交结果和最终查询日志 | 未执行 |

测试不关闭约束、不提前提交无绑定区间，也不使用真实业务数据库、真实凭据或业务数据。
