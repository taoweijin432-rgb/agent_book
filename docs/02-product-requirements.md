## 1. 角色与权限原则

| 角色 | 核心职责 | 可写范围 | 明确禁止 |
|---|---|---|---|
| 作者/用户 | 定义作品意图、审批候选内容、处理冲突和发布章节 | 作者设计、审批决定、允许的人工修订 | 绕过提交协议直接篡改已提交事实，除非走审计化强制覆盖 |
| 规划 Agent | 将设计意图编译为大纲、场景目标和任务建议 | 只能提交规划提案或草稿 | 直接提交 `Canonical Text Version`、`Story Event`、`Canon Fact` 或 `State Transition`、直接改变作者设计源 |
| 写作 Agent | 按场景任务生成候选正文和状态变更提案 | 只能写入草稿暂存区和候选提案 | 直接更新 Canon 叙事源、读取未授权秘密、任意写表 |
| 校验 Agent/服务 | 抽取候选事件、执行硬校验和软评测 | 校验结果、修复建议和修复候选 | 以模型判断绕过原子提交或默默修改权威数据 |
| 提交服务 | 在受控事务中提交正文、事件、状态和审计 | 受限领域写操作 | 代替作者做未授权的文学决策 |

权限以领域能力和场景权限表达，不笼统定义为“Agent 与用户权限完全相同”。

## 2. 主要使用流程

从新建小说到章节发布的主流程为：作者创建项目并录入设计源；规划章节、剧情弧和场景；系统生成场景任务；上下文组装器依据任务、视角和权限形成上下文包；写作 Agent 生成候选正文和状态变更提案；校验服务先抽取 Narrative Assertion，再形成候选事件/事实/状态变化并执行硬/软检查；系统进行局部修复或请求人工处理；作者审批或拒绝；提交服务以一个逻辑事务提交正文、事件、状态变更和审计；索引更新作为可重建投影异步进行；作者在需要时修改、回退或重演。

正文“生成完成”不等于 Canon 内容成立；只有正式提交完成后，Canon 正文记录、已确认故事事件和状态变化才进入 Canon 叙事源，详见 `04` 和 `08`。

## 3. 功能需求

### 3.1 项目、设计和规划

- **FR-001** 系统必须支持创建单用户小说项目，并建立小说、卷、章、场景的层级关系。
- **FR-002** 系统必须支持管理世界规则、人物设计、地点、组织、物品、剧情弧、大纲节点、伏笔、秘密和结局约束。
- **FR-003** 系统必须为作者设计对象保留稳定身份、版本、来源和失效语义，设计修改不得静默覆盖历史版本。
- **FR-004** 系统必须支持将大纲节点映射到场景目标、故事事件和完成状态；映射不等同于自动证明目标已完成。
- **FR-005** 系统必须支持伏笔从设计、埋设、推进、回收、废弃到作者确认的生命周期。
- **FR-006** 系统必须支持作者标记秘密的可见范围、触发条件和安全写作约束，不得把秘密真相默认放入写作上下文。

### 3.2 场景规划、生成与上下文

- **FR-007** 系统必须创建包含场景目标、参与人物、视角、时间地点、允许事实、禁止泄露项和输出要求的场景任务。
- **FR-008** 系统必须将场景任务编译为可追踪的上下文包；每个条目记录来源、版本、权限依据和入选理由。
- **FR-009** 系统必须支持写作 Agent 生成候选正文和状态变更提案，并将其置于草稿暂存区。
- **FR-010** 写作 Agent 只能读取场景所需的授权信息；系统必须对人物视角和秘密权限进行过滤。
- **FR-011** 系统应支持结构化查询、关键词检索和向量检索的组合；相似度只能作为召回信号，不能直接证明事实成立。
- **FR-012** 系统必须记录 Prompt 版本、模型调用、工具调用、`context_bundle_id`、上下文内容摘要/hash、上下文版本，以及受权限保护的完整上下文包或可恢复引用、输出引用和成本数据；日志不得默认暴露秘密原文。

### 3.3 校验、修复与审批

- **FR-013** 系统必须按两阶段处理候选正文：先从 `Candidate Version` 抽取 `Narrative Assertion`，再根据断言形成 `Candidate Event`、`Candidate Fact Proposal` 和 `Candidate State Transition`，并保留正文证据；上述 Candidate 对象在校验、审批和 Canon Commit 前均不是 Canon 对象，Canon Commit 成功后才分别形成或映射为 `Story Event`、`Canon Fact` 和 `State Transition`。
- **FR-014** 系统必须执行硬约束校验，至少覆盖世界规则、身份、知识权限、时间线、地点、物品、关系和秘密泄露。
- **FR-015** 系统应执行软质量评测，至少覆盖人物性格/语言、能力、因果、剧情目标、伏笔、视角和文风。
- **FR-016** 硬错误默认必须阻断正式提交；强制覆盖只能在新的 `Author Design Revision` 已生效，或有效的 `Constraint Exception` 已存在时发生。例外至少记录适用范围、覆盖原因、生效版本、到期条件或撤销状态、创建者及审计信息；缺少上述依据时，硬冲突候选不得提交为 Canon。当前自动审批默认关闭，只有质量基准集、阈值、规则版本和授权策略正式确认后才能启用；普通 Approval Record 不能单独覆盖硬约束，只能批准已经引用生效设计修订或有效 Constraint Exception 的候选。
- **FR-017** 系统应支持局部修复，并在修复后重新抽取和校验；不得只修改评分而不重新验证候选正文、`Narrative Assertion` 及其候选事件、事实和状态变化提案。
- **FR-018** 系统必须支持作者审批、拒绝、要求重写、人工编辑和强制覆盖等操作，并区分各操作的权限与审计要求。人工编辑候选正文必须产生新的候选版本；正文内容发生变化后，原校验结果和原审批自动失效，必须重新校验和审批。

**校验与审批失效规则：** 以下任一对象发生变化，都必须使旧校验结果和旧审批结果失效：候选正文版本、状态变更提案、`Author Design Revision`、`Canon Watermark`、校验策略或校验器版本、校验运行本身绑定的关键输入。失效后必须生成新的候选版本或新的校验运行，并重新完成校验和审批；不得复用旧批准结果完成提交。

### 3.4 正式提交、版本和发布

- **FR-019** 正文、故事事件和状态变更必须经过同一正式提交边界；Approval Record 和提交必须绑定 `Candidate Version`、正文内容 hash、`Validation Run`、`Context Bundle`、`Author Design Revision`、`Canon Watermark`、审批策略版本及其不可变引用，提交结果应可重放和审计。
- **FR-020** 系统必须支持幂等键、重复提交识别、一致读取边界冲突检测和并发场景保护；一致读取边界至少必须固定 `Author Design Revision` 和 `Canon Watermark`，并能追溯 `Scene Task Version` 与 `Context Bundle`。与审批和提交绑定的一致输入至少包括 `Candidate Version`、Candidate 内容 hash、`Validation Run`、`Context Bundle`、`Author Design Revision`、`Canon Watermark` 和审批策略版本；人工编辑或 Candidate 内容变化后，旧校验和旧审批必须失效。
- **FR-021** 系统必须支持回退到已确认版本，并产生新的补偿/失效记录，不得物理删除历史证据。
- **FR-022** 已发布章节的修改必须走受控修订流程，明确对后续事实、索引、伏笔和大纲映射的影响。
- **FR-023** 图关系和向量索引更新失败不得使权威 Canon 处于不明状态；索引必须可重建并有失败重试记录。

### 3.5 追踪与人工控制

- **FR-024** 系统必须能从需求追踪到架构组件、数据对象、校验规则和后续测试案例。
- **FR-025** 系统必须提供 Canon Fact、Narrative Assertion、事件、状态、设计、上下文和提交的来源链路。
- **FR-026** 系统必须支持人工查询“为什么该上下文进入模型”“为什么该候选被阻断”“哪个版本确认了该事实”。
- **FR-027** 系统应记录人工修改差异、修改者、修改原因、影响范围和再次校验结果。

## 4. 非功能需求

- **NFR-001 可追溯性**：所有 Canon Fact、`Story Event` 和状态变更必须可追溯到正文片段、`Canon Commit`、来源版本、`Validation Run` 和 `Approval Record`。
- **NFR-002 一致性**：正文与对应事件/状态变更的正式提交必须具有明确原子边界；部分成功不得被呈现为完整成功。
- **NFR-003 安全性**：秘密和未授权设计不得通过上下文、检索结果、错误信息或常规日志泄露。
- **NFR-004 可重放性**：给定 `Scene Task Version`、`Author Design Revision`、`Canon Watermark`、Context Bundle 的实际内容或受保护不可变引用、Prompt 版本、模型版本及参数、工具版本和外部调用记录，系统应能重建原始输入与执行链路，并保留 `Candidate Version` 原始内容及其来源链；重新调用外部模型不承诺得到逐字相同输出，模型非确定性、检索变化、外部依赖变化和人工介入必须显式标记。
- **NFR-005 可恢复性**：权威数据可从备份/版本恢复，图和向量索引可由权威数据重建。
- **NFR-006 可观测性**：记录请求、Trace、校验、工具、Token、成本、耗时、人工修改和评测结果；秘密字段遵循脱敏策略。
- **NFR-007 可扩展性**：百万字级容量通过分层事实和按需召回实现，不要求单次上下文容纳全书。
- **NFR-008 可解释性**：硬错误必须附带规则、证据、版本和建议修复方向；软评测需标记模型/规则来源与不确定性。
- **NFR-009 可维护性**：优先保持技术中立和单体/模块化边界，只有基准测试证明需要时才引入复杂中间件。
- **NFR-010 成本与时延**：持续记录每千字成本、生成/校验耗时和端到端时延；正式阈值待通过基准测试确定。

## 5. 验收条件与追踪

初步验收条件：

1. 能完成一个小型小说从设计、场景任务、候选正文、校验到正式提交的闭环。
2. 写作 Agent 的工具能力无法直接更新 Canon 叙事源对象。
3. 草稿被拒绝时不会进入 Canon 叙事源；正式提交失败时不存在“正文已生效、状态未生效”的对外成功状态。
4. 构造身份、时间线、秘密、地点和物品冲突样例时，系统能按 `03` 的分类输出证据和阻断结果。
5. 上下文审计能显示每个条目的来源、版本、权限依据和入选原因。
6. 删除/失效、回滚、索引失败和旧任务重放均有可验证的结果。

需求追踪关系为：`FR/NFR → 05` 组件与调用链 → `06` 对象/证据 → `08` 提交状态 → 后续测试案例。未建立测试案例的需求仍视为未完成，不得以文档存在代替验证。
